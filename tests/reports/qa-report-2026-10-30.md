## STEP 2: Verification Vulnerability Analysis (CRITICAL)

### 1. Vulnerability Overview
- **Vulnerable Endpoint**: `POST /api/auth` (and legacy compatibility paths `/backend/api/auth.php`, `/auth.php`)
- **File and Lines**: [backend/src/routes/authRoutes.ts](file:///E:/AquaLicious/backend/src/routes/authRoutes.ts#L142-L183)
- **Secondary Endpoints / Middleware Involved**:
  - `POST /api/auth/resend-verification` in [backend/src/routes/authRoutes.ts](file:///E:/AquaLicious/backend/src/routes/authRoutes.ts#L352-L401)
  - `authenticate` and `requireEmailVerified` in [backend/src/middleware/auth.ts](file:///E:/AquaLicious/backend/src/middleware/auth.ts#L31-L89)
  - Frontend fallback in [frontend/src/pages/VerifyEmailCompletePage.tsx](file:///E:/AquaLicious/frontend/src/pages/VerifyEmailCompletePage.tsx#L54-L67)

### 2. Vulnerability Mechanics
In `backend/src/routes/authRoutes.ts`, lines 142-183 handle `action === 'verify_email'`:
```typescript
if (action === 'verify_email') {
  const { email } = req.body;
  const user = await prisma.user.findFirst({
    where: { OR: [{ email: cleanEmail }, { username: cleanEmail }] }
  });
  const updated = await prisma.user.update({
    where: { id: user.id },
    data: { emailVerified: true }
  });
  const token = generateTestToken({
    uid: updated.firebaseUid,
    email: updated.email,
    role: 'CUSTOMER',
    email_verified: true
  });
  return res.status(200).json({ token, user: ... });
}
```
1. **Unauthenticated Access**: The endpoint requires zero authentication, headers, OTPs, or action codes.
2. **Arbitrary User Lookup**: An unauthenticated caller specifies any email or username (including `aqualiciousadmin@gmail.com` or `admin`).
3. **Database Mutation**: The user's database status is directly updated to `emailVerified: true`.
4. **Token Minting & Full Admin Takeover**:
   - The route calls `generateTestToken` using the backend's secret (`config.jwtSecret`) for the user's `firebaseUid`.
   - When the caller uses this token to access protected routes (`Authorization: Bearer <token>`), `authenticate` in `backend/src/middleware/auth.ts` verifies the signature and queries the database for `firebaseUid`.
   - Because `user.role` is read from PostgreSQL (`Role.ADMIN`), `req.user.role` is set to `Role.ADMIN`.
   - The unauthenticated caller is instantly granted full Administrator privileges across `/api/users`, `/api/inventory`, `/api/sales`, etc.

### 3. Exact Reproduction Steps (Local Isolated Environment Only)
1. Send an unauthenticated POST request to verify the admin user:
   ```bash
   curl -s -X POST http://127.0.0.1:18088/api/auth \
     -H "Content-Type: application/json" \
     -d '{"action":"verify_email","email":"aqualiciousadmin@gmail.com"}'
   ```
2. Extract the returned `token` string from the JSON response.
3. Access the restricted Administrator users endpoint with the received token:
   ```bash
   curl -s http://127.0.0.1:18088/api/users \
     -H "Authorization: Bearer <TOKEN>"
   ```
4. **Result**: HTTP 200 OK returning all system users and roles, confirming full administrative account takeover.

### 4. Impact Assessment
- **Critical (Account Takeover)**: Complete takeover of Administrator and Customer accounts without credentials.
- **High (Validation Bypass)**: Completely bypasses `requireEmailVerified` (`EMAIL_NOT_VERIFIED` check) across all endpoints.
- **High (Data Integrity)**: Arbitrary email addresses can be marked verified without proving inbox ownership.
- **High (Exploit Chaining)**: Can be chained with consent omission to place unauthorized orders and submit unvalidated payment proofs.

### 5. Proposed Defensive Remediation
1. **Remove Insecure Endpoint**: Completely delete the `action === 'verify_email'` block in `backend/src/routes/authRoutes.ts`.
2. **Authoritative Verification**: Verification status must only originate from verified Google Firebase ID tokens (`claims.email_verified === true`).
3. **Enforce in Auth Middleware**: The `authenticate` middleware should only sync `emailVerified: true` when `decodedToken.email_verified === true` from Firebase Admin SDK.
4. **Remove Frontend Fallback**: In `frontend/src/pages/VerifyEmailCompletePage.tsx`, delete `verifyViaBackend` and require standard Firebase `applyActionCode`.

3. CORS configuration contains wildcard domain suffix matching that exposes the API to any `.vercel.app` or `.ngrok` site.
4. Payment proof uploads lack strict image validation, permitting SVG files which can be used for Stored XSS against administrators.

#### 1.5 Legacy Redirects & Query String Preservation
- **Exact Layer Dropping Query**: Client-side React Router v6 in `frontend/src/App.tsx` (lines 253–296).
- **Technical Explanation**: Express and Vercel route rewrites passed requests through to the single-page application. In `App.tsx`, legacy route entries were declared as:
  ```tsx
  <Route path="/verify-email-complete.html" element={<Navigate to="/verify-email-complete" replace />} />
  ```
  React Router's `<Navigate to="..." replace />` evaluates only the pathname by default and drops `location.search` (`?mode=verifyEmail&oobCode=...`).
- **Fix**: Implemented `PreserveQueryRedirect`:
  ```tsx
  function PreserveQueryRedirect({ to }: { to: string }) {
    const location = useLocation();
    return <Navigate to={{ pathname: to, search: location.search, hash: location.hash }} replace />;
  }
  ```
- **Test Verification**: Added test asserting `/verify-email-complete.html?mode=verifyEmail&oobCode=test-code` preserves query parameters and action code. (PASS)

### 2. Phase 3 Remediations & Results

#### 2.1 Asia/Manila Date Grouping in `reportService.ts`
- **Issue**: Historical orders placed around midnight (e.g., 23:30 and 00:30 Asia/Manila time) were being bucketed into incorrect calendar days when the database or server parsed timestamps in UTC.
- **Fix**: Replaced UTC date string formatting with `Intl.DateTimeFormat('en-CA', { timeZone: 'Asia/Manila' })` and computed Manila midnight boundaries with exact PHT offsets (+08:00).
- **Test**: Seeded orders at 23:30 PHT and 00:30 PHT; verified daily sales reports bucketed them into two distinct calendar days. (PASS)

#### 2.2 PostgreSQL Transient Connection Reset Recovery
- **Issue**: Unhandled PostgreSQL socket disconnects or connection resets crashed the Node.js process.
- **Fix**: In `backend/src/server.ts`, added global error handling and `process.on('unhandledRejection')` catching Prisma connection error codes (`P1001`, `P1002`, `P1017`, `ECONNRESET`). Returns HTTP 503 `DATABASE_UNAVAILABLE` with `Retry-After: 1` header, triggers non-blocking `prisma.$connect()`, and keeps the server process running.
- **Test**: Simulated `P1017` connection reset; verified server returned HTTP 503 with `Retry-After` header and stayed alive for subsequent requests. (PASS)
